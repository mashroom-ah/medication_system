# «Мой приём» — система учёта лекарств

«Мой приём» — учебное приложение на Python для учёта лекарственных препаратов, расписаний их приёма и истории фактических приёмов. Проект включает консольную версию и веб-интерфейс на Django.

В рамках практических работ № 6 и № 7 веб-интерфейс был организован с использованием шаблонов Django Template Language (DTL), а хранение данных веб-приложения дополнено реляционной базой данных SQLite. Для работы с базой на данном этапе используется стандартная библиотека Python `sqlite3`, без Django ORM.

## 1. Назначение и возможности проекта

Проект предназначен для ведения сведений о пользователях, лекарственных препаратах, расписаниях их приёма и фактических приёмах.

### 1.1. Возможности консольной версии

Консольная версия позволяет:

- добавлять, искать, просматривать и сортировать пользователей;
- добавлять, искать, фильтровать по дозировке и сортировать лекарства;
- создавать и просматривать расписания приёма;
- проверять наступление времени приёма;
- фиксировать фактический приём лекарства;
- отменять запись о приёме с сохранением истории;
- просматривать записи о приёмах за выбранную дату;
- сохранять данные между запусками в JSON-файлах.

Консольная версия запускается через `main.py` и использует предметные классы из каталога `models/` и модуль `storage.py`.

### 1.2. Возможности веб-интерфейса

Веб-интерфейс на Django предоставляет следующие возможности:

- просмотр главной страницы и переход к разделам приложения;
- просмотр списка лекарств и поиск по названию;
- фильтрация лекарств по минимальной дозировке;
- просмотр подробной информации об отдельном лекарстве;
- просмотр расписаний и связанных с ними данных;
- отображение статуса приёма;
- просмотр подробной информации о расписании;
- просмотр истории приёмов и подробной информации об отдельной записи;
- фильтрация истории приёмов по дате;
- просмотр страницы статистики, сформированной на основе SQL-запросов;
- обработка неизвестных URL и отсутствующих объектов с ответом HTTP 404.

Веб-интерфейс предназначен преимущественно для просмотра и фильтрации данных. Создание, редактирование и удаление предметных записей через Django-формы не реализованы. Операции предметной логики доступны в консольной версии.

## 3. Предметная область

Предметная область проекта — персональный учёт лекарств и контроль их приёма.

В каталоге `models/` находятся классы предметной области:

- **`User`** (`models/users.py`) — пользователь: идентификатор, имя и возраст;
- **`Medicine`** (`models/medicines.py`) — лекарственный препарат: идентификатор, название, дозировка и единица измерения;
- **`Schedule`** (`models/schedules.py`) — расписание приёма, связанное с пользователем и лекарством, с указанием часа и минуты;
- **`Intake`** (`models/intakes.py`) — запись о фактическом приёме, связанная с расписанием, датой и признаком выполнения.

Классы `Schedule` и `Intake` используют связи между объектами предметной области. Методы `to_data()` и `from_data()` применяются для преобразования объектов в данные и обратно.

Эти классы являются собственными классами предметной области, а не моделями Django ORM.

## 5. Веб-интерфейс и маршрутизация

Веб-часть реализована на Django. Представления получают данные, подготавливают контекст и передают его шаблонам с помощью `render()`.

### 5.1. Основные URL

| URL | Назначение | Представление |
|---|---|---|
| `/` | Главная страница | `homepage.views.index()` |
| `/statistics/` | Статистика | `homepage.views.statistics()` |
| `/medicines/` | Список лекарств, поиск и фильтрация | `medicines.views.medicines()` |
| `/medicines/<medicine_id>/` | Подробная информация о лекарстве | `medicines.views.medicine_detail()` |
| `/schedules/` | Список расписаний | `schedules.views.schedules()` |
| `/schedules/<schedule_id>/` | Подробная информация о расписании | `schedules.views.schedule_detail()` |
| `/intakes/` | История приёмов | `intakes.views.intakes()` |
| `/intakes/<intake_id>/` | Подробная информация о записи | `intakes.views.intake_detail()` |
| `/admin/` | Стандартная административная страница Django | Django Admin |

В маршрутах используются именованные URL и пространства имён приложений: `homepage`, `medicines`, `schedules` и `intakes`.

Поиск лекарств выполняется через параметр `q`, например:

```text
/medicines/?q=аспирин
```

Фильтр минимальной дозировки использует параметр, предусмотренный представлением лекарств.

Для фильтрации истории приёмов по дате используется параметр `date`, например:

```text
/intakes/?date=2026-09-13
```

Дата в примере служит иллюстрацией формата запроса. Результат зависит от наличия соответствующих записей в базе.

### 5.2. Обработка отсутствующих страниц и объектов

В корневой маршрутизации Django настроен обработчик `homepage.views.page_not_found`. Для отсутствующего объекта на детальной странице используется обработка HTTP 404. Это позволяет возвращать корректный ответ вместо отображения несуществующей записи.

## 6. Django Template Language (DTL)

### 6.1. Базовый шаблон и наследование

Общий шаблон находится в `templates/base.html`. Он содержит базовую HTML-структуру, подключение Bootstrap и собственных статических файлов, навигацию, блоки заголовка и основного содержимого, а также подвал.

Дочерние шаблоны используют наследование:

```django
{% extends "base.html" %}
```

Заголовок страницы и её содержимое определяются блоками:

```django
{% block title %}Название страницы{% endblock %}

{% block content %}
    <!-- Содержимое конкретной страницы -->
{% endblock %}
```

Это позволяет сохранять единое оформление сайта и не дублировать общую HTML-разметку на каждой странице.

### 6.2. Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные файлы и подключаются директивой `{% include %}`:

- `templates/includes/navigation.html` — основная навигация;
- `medicines/templates/medicines/includes/medicine_card.html` — карточка лекарства;
- `schedules/templates/schedules/includes/schedule_card.html` — карточка расписания;
- `intakes/templates/intakes/includes/intake_status.html` — отображение статуса записи о приёме.

### 6.3. Контекст, циклы и условия

Представления передают данные в шаблоны через словарь контекста. В шаблонах используются:

- `{{ ... }}` — вывод значений;
- `{% for %}` — перебор списков;
- `{% if %}` — проверка условий;
- `{% empty %}` — отображение содержимого при пустой коллекции.

Фильтры DTL используются для форматирования и вывода данных, а не для реализации бизнес-логики. Например:

```django
{{ medicines|length }}
{{ medicine.name|default:"Без названия" }}
```

Фильтр `length` позволяет вывести количество элементов, а `default` — подставить значение по умолчанию, если исходное значение отсутствует или пусто.

## 8. Хранение данных после ПР7

После выполнения ПР7 проект использует два способа хранения данных, предназначенных для разных частей приложения:

1. **JSON-файлы** — исходные данные и хранилище консольной версии, сохранённые с предыдущих практических работ.
2. **SQLite** — реляционная база, из которой Django-представления получают предметные данные веб-интерфейса.

Консольная версия продолжает использовать `storage.py` и классы из `models/`. Веб-представления обращаются к SQLite через `db/database.py` и библиотеку `sqlite3`.

Предметные классы из `models/` не являются моделями Django ORM. На этапе ПР7 таблицы предметной базы создаются SQL-командами из `sql/schema.sql`.

## 9. Структура базы данных SQLite

Файл базы данных:

```text
data/medication.sqlite
```

SQL-команды создания таблиц находятся в `sql/schema.sql`.

### 9.1. Таблица `users`

Хранит сведения о пользователях.

| Поле | Тип SQLite | Назначение и ограничения |
|---|---|---|
| `id` | `INTEGER` | Первичный ключ |
| `name` | `TEXT` | Имя пользователя, обязательное поле |
| `age` | `INTEGER` | Возраст; ограничение от 1 до 120 |

### 9.2. Таблица `medicines`

Хранит сведения о лекарственных препаратах.

| Поле | Тип SQLite | Назначение и ограничения |
|---|---|---|
| `id` | `INTEGER` | Первичный ключ |
| `name` | `TEXT` | Название лекарства, обязательное поле |
| `dosage` | `REAL` | Дозировка, должна быть больше нуля |
| `unit` | `TEXT` | Единица измерения, обязательное поле |

### 9.3. Таблица `schedules`

Хранит расписания приёма лекарств.

| Поле | Тип SQLite | Назначение и ограничения |
|---|---|---|
| `id` | `INTEGER` | Первичный ключ |
| `user_id` | `INTEGER` | Внешний ключ на `users.id` |
| `medicine_id` | `INTEGER` | Внешний ключ на `medicines.id` |
| `hour` | `INTEGER` | Час приёма, от 0 до 23 |
| `minute` | `INTEGER` | Минута приёма, от 0 до 59 |

Внешний ключ `user_id` связывает расписание с пользователем. Внешний ключ `medicine_id` связывает расписание с лекарством.

### 9.4. Таблица `intakes`

Хранит историю фактических приёмов.

| Поле | Тип SQLite | Назначение и ограничения |
|---|---|---|
| `id` | `INTEGER` | Первичный ключ |
| `schedule_id` | `INTEGER` | Внешний ключ на `schedules.id` |
| `intake_date` | `TEXT` | Дата приёма в строковом формате длиной 10 символов |
| `taken` | `INTEGER` | Признак выполнения: `0` или `1`, по умолчанию `1` |

Внешний ключ `schedule_id` связывает запись истории с соответствующим расписанием.

### 9.5. Первичные и внешние ключи

Первичный ключ (`PRIMARY KEY`) однозначно идентифицирует каждую запись таблицы. Внешний ключ (`FOREIGN KEY`) связывает запись с другой таблицей и позволяет контролировать ссылочную целостность.

В проекте заданы следующие связи:

- `schedules.user_id` → `users.id`;
- `schedules.medicine_id` → `medicines.id`;
- `intakes.schedule_id` → `schedules.id`.

Для внешних ключей используются ограничения `ON UPDATE CASCADE` и `ON DELETE RESTRICT`. Они задают поведение при изменении идентификаторов и удалении связанных записей.

В схеме также присутствуют ограничения `CHECK`, которые проверяют допустимые значения, и индексы для часто используемых полей.

## 10. Модуль подключения к базе данных

Модуль `db/database.py` отвечает за подключение к SQLite.

Он определяет путь к файлу базы относительно каталога проекта, создаёт каталог базы при необходимости и предоставляет функцию `get_connection()`.

При открытии соединения выполняются следующие настройки:

- устанавливается `sqlite3.Row` как формат строк результата;
- включается проверка внешних ключей с помощью `PRAGMA foreign_keys = ON`.

`sqlite3.Row` позволяет обращаться к полям результата запроса по именам столбцов, а не только по числовым индексам.

Функция `initialize_database()` выполняет SQL-команды из `sql/schema.sql`, создавая отсутствующие таблицы.

## 11. Импорт данных из JSON

Перенос данных из JSON в SQLite выполняется скриптом `db/import_json.py`.

Скрипт:

1. читает JSON-файлы пользователей, лекарств, расписаний и истории приёмов;
2. создаёт таблицы по SQL-схеме, если они ещё не созданы;
3. очищает существующие записи в порядке, учитывающем связи между таблицами;
4. вставляет данные в SQLite;
5. фиксирует изменения через `commit()`;
6. при возникновении ошибки выполняет `rollback()` и повторно передаёт исключение.

Для пакетной вставки используется `executemany()`, а значения передаются в SQL с помощью заполнителей `?`.

Импорт выполняется командой из корневой папки проекта:

```bash
python -m db.import_json
```

При повторном запуске содержимое таблиц заново загружается из JSON. Поэтому не следует запускать импорт после ручного редактирования базы, если эти изменения необходимо сохранить.

## 12. SQL-запросы

Все учебные SQL-запросы проекта находятся в файле `sql/queries.sql`.

В нём представлены 13 запросов, демонстрирующих основные операции SQL, необходимые для выполнения ПР7.

| № | Назначение | Используемые конструкции |
|---:|---|---|
| 1 | Список лекарств | `SELECT`, `ORDER BY` |
| 2 | Список пользователей по возрасту | `SELECT`, `ORDER BY` |
| 3 | Поиск лекарств по части названия | `WHERE`, `LIKE`, параметр `?` |
| 4 | Фильтрация по минимальной дозировке | `WHERE`, сравнение, параметр `?` |
| 5 | Расписания выбранного пользователя | `WHERE` |
| 6 | История приёмов за дату | `WHERE` |

| 8 | Подробная история приёмов | несколько `JOIN` |

| 10 | Средняя и максимальная дозировка | `AVG()`, `MAX()` |
| 11 | Количество расписаний по лекарствам | `LEFT JOIN`, `GROUP BY`, `COUNT()` |
| 12 | Количество приёмов по статусу | `GROUP BY`, `COUNT()` |
| 13 | Лекарства, назначенные более чем в заданном количестве расписаний | `JOIN`, `GROUP BY`, `HAVING` |

Таким образом, SQL-часть включает выборки списков, фильтрацию с помощью `WHERE`, соединение таблиц, агрегатные функции и группировку. Некоторые запросы используют несколько конструкций одновременно.

### 12.1. Параметризованные запросы

Параметризованные запросы отделяют текст SQL-команды от передаваемых значений. Вместо вставки пользовательского ввода непосредственно в SQL используются заполнители `?`.

Например:

```python
cursor.execute(
    "SELECT id, name FROM medicines WHERE name LIKE ?",
    (pattern,)
)
```

Здесь `pattern` передаётся отдельно от SQL-команды. Такой подход помогает избежать SQL-инъекций и корректно передавать значения в запросы.

В проекте параметризованные запросы используются для поиска лекарств, фильтрации по дозировке, выбора расписаний и фильтрации истории по дате.

## 13. Использование SQLite в Django-представлениях

Django-представления выполняют SQL-запросы через модуль подключения `db/database.py`, получают результаты и передают их в HTML-шаблоны через контекст.

На данном этапе предметные данные не загружаются через Django ORM: запросы к таблицам `users`, `medicines`, `schedules` и `intakes` выполняются напрямую через `sqlite3`.

### 13.1. Страницы, использующие SQLite

- **Главная страница `/`** — главная страница приложения.
- **Список лекарств `/medicines/`** — получает список лекарств из SQLite; поддерживает поиск по названию и фильтрацию по минимальной дозировке.
- **Карточка лекарства `/medicines/<id>/`** — получает подробные данные об отдельном лекарстве.
- **Список расписаний `/schedules/`** — использует связанные данные о пользователях и лекарствах и отображает статус приёма.
- **Карточка расписания `/schedules/<id>/`** — показывает подробности выбранного расписания.
- **История приёмов `/intakes/`** — выводит записи из SQLite и поддерживает фильтрацию по дате.
- **Карточка записи `/intakes/<id>/`** — показывает подробности записи с использованием связанных данных.
- **Статистика `/statistics/`** — выводит показатели, вычисленные SQL-запросами.

Результаты запросов передаются шаблонам через контекст. В представлениях используются параметризованные значения, а в шаблонах — переменные и циклы DTL для отображения результатов.
