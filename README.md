# «Мой приём»

**«Мой приём»** — веб-приложение для учёта лекарств, управления расписанием приёма и ведения истории выполнения назначений.

Приложение помогает хранить информацию о пользователях и лекарствах, составлять индивидуальные расписания и отслеживать, какие приёмы были выполнены, пропущены или отменены.

## Возможности

- **Пользователи:** ведение списка пользователей приложения.
- **Каталог лекарств:** хранение названий, дозировок и единиц измерения.
- **Расписание приёма:** создание расписаний с указанием пользователя, лекарства и времени приёма.
- **История приёмов:** фиксация фактического результата каждого запланированного приёма.
- **Статусы приёма:** отметки «Принято», «Пропущено» и «Отменено».
- **Поиск и фильтрация:** поиск лекарств и фильтрация истории по дате, пользователю, лекарству и статусу.
- **Сортировка и пагинация:** удобная работа со списками записей.
- **Статистика:** получение сводной информации о расписаниях и истории приёмов.
- **Администрирование:** управление данными через встроенную административную панель Django.

## Структура проекта

Проект разделён на приложения, каждое из которых отвечает за отдельную часть функциональности.

| Приложение | Назначение |
|---|---|
| `homepage` | Пользователи и главная страница |
| `medicines` | Каталог лекарств |
| `schedules` | Расписания приёма |
| `intakes` | История фактических приёмов |
| `medication_site` | Настройки проекта и маршрутизация |

### Связи между сущностями

Основные сущности приложения связаны внешними ключами:

- Один пользователь может иметь несколько расписаний.
- Одно лекарство может использоваться в нескольких расписаниях.
- Одно расписание может содержать несколько записей истории приёма.

Таким образом, расписание связывает пользователя с выбранным лекарством, а история приёмов позволяет отслеживать выполнение этого расписания.

## Модели данных

В основе проекта лежат четыре основные модели: `User`, `Medicine`, `Schedule` и `Intake`. Они описывают пользователей системы, лекарства, расписания приёма и историю выполнения приёмов.

### 1. User — пользователь

**Приложение:** `homepage`

Модель `User` представляет пользователя приложения «Мой приём». Она используется для связи расписаний с конкретным человеком.

Основная задача модели — хранить данные пользователя и обеспечивать возможность получить все расписания, относящиеся к нему.

Важно: `homepage.User` — это модель пользователя предметной области проекта. Она не является встроенной моделью авторизации Django (`django.contrib.auth.models.User`).

### 2. Medicine — лекарство

**Приложение:** `medicines`

Модель `Medicine` хранит информацию о лекарственных препаратах.

Она используется при создании расписаний: одно лекарство может быть связано с несколькими расписаниями.

В модели реализовано поле `slug`:

- используется для формирования понятных URL;
- создаётся на основе названия лекарства;
- для преобразования русских букв используется библиотека `Unidecode`;
- значение должно быть уникальным;
- для получения адреса объекта используется метод `get_absolute_url()`.

Например, вместо ссылки с числовым идентификатором можно использовать адрес с понятным названием лекарства.

### 3. Schedule — расписание приёма

**Приложение:** `schedules`

Модель `Schedule` описывает расписание приёма определённого лекарства пользователем.

Она связывает две другие модели:

- `User` — человека, для которого создано расписание;
- `Medicine` — лекарство, которое необходимо принимать.

Таким образом, каждое расписание относится к конкретному пользователю и конкретному лекарству.

В модели также предусмотрены вычисляемые поля:

- `total_minutes` — общее количество минут, рассчитываемое на основе данных расписания;
- `is_night` — признак ночного расписания, вычисляемый на стороне базы данных.

Для вычисления этих значений используется `GeneratedField`. Это позволяет базе данных автоматически поддерживать вычисляемые значения при изменении исходных полей.

### 4. Intake — история приёмов

**Приложение:** `intakes`

Модель `Intake` хранит информацию о выполнении запланированных приёмов лекарства.

Каждая запись связана с определённым расписанием через `ForeignKey` к модели `Schedule`.

Вместо простого логического поля, которое могло бы хранить только два состояния, для результата приёма используется набор вариантов `TextChoices`:

- `taken` — лекарство принято;
- `missed` — приём пропущен;
- `skipped` — приём отмечен как пропущенный пользователем.

Такой подход позволяет хранить несколько вариантов состояния и отображать их в понятном виде.

### Связи между моделями

Основные связи проекта можно представить следующим образом:

```text
User
  |
  | 1 : N
  v
Schedule
  |
  | N : 1
  v
Medicine

Schedule
  |
  | 1 : N
  v
Intake
```

- Один пользователь может иметь несколько расписаний.
- Одно лекарство может использоваться в нескольких расписаниях.
- Одно расписание может иметь несколько записей в истории приёмов.
- Каждая запись истории относится к одному расписанию.

Связи реализованы с помощью `ForeignKey` Django ORM. Это позволяет обращаться к связанным объектам через ORM, выполнять фильтрацию по связанным полям и получать связанные записи.

### Особенности реализации моделей

В проекте используются следующие возможности Django ORM:

| Возможность | Где используется | Назначение |
|---|---|---|
| `ForeignKey` | `Schedule`, `Intake` | Связь между моделями |
| `TextChoices` | `Intake` | Набор допустимых статусов приёма |
| `GeneratedField` | `Schedule` | Вычисляемые поля на стороне БД |
| `SlugField` | `Medicine` | Уникальный адресный идентификатор |
| `get_absolute_url()` | `Medicine` | Получение URL объекта |
| Миграции | Все приложения | Управление изменениями структуры БД |

Изменения структуры моделей сохраняются в миграциях Django. Благодаря этому структуру базы данных можно последовательно обновлять командой:

```powershell
python manage.py migrate
```

Проверить состояние миграций можно командой:

```powershell
python manage.py showmigrations
```


## Установка и запуск

### Требования

- Python 3.10 или новее.
- pip.
- SQLite 3.31 или новее для поддержки вычисляемых столбцов.

### 1. Клонирование проекта

```bash
git clone <URL-репозитория>
cd medication_system
```

### 2. Создание виртуального окружения

**Windows PowerShell:**

```powershell
py -m venv venv
.\venv\Scripts\Activate.ps1
```

Если PowerShell блокирует активацию:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\venv\Scripts\Activate.ps1
```

**Linux/macOS:**

```bash
python3 -m venv venv
source venv/bin/activate
```

### 3. Установка зависимостей

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Подготовка базы данных

```bash
python manage.py check
python manage.py migrate
```

### 5. Создание учётной записи администратора

```bash
python manage.py createsuperuser
```

Следуй инструкциям в терминале, чтобы задать имя пользователя и пароль.

### 6. Запуск сервера

```bash
python manage.py runserver
```

После запуска приложение будет доступно по адресу:

http://127.0.0.1:8000/

Административная панель:

http://127.0.0.1:8000/admin/

## Административная панель

Для управления данными используется Django Admin.

Через административную панель можно:

- добавлять и редактировать пользователей;
- управлять каталогом лекарств;
- создавать и изменять расписания;
- просматривать историю приёмов;
- работать со связанными записями непосредственно в формах родительских объектов.

Для входа используется учётная запись суперпользователя, созданная командой `createsuperuser`.

## Работа с данными

Для взаимодействия с базой данных используется Django ORM.

В проекте применяются:

- фильтрация и исключение записей;
- поиск по связанным моделям;
- сортировка и постраничное отображение;
- объединение связанных данных;
- агрегирование и подсчёт записей;
- оптимизация запросов с помощью `select_related`, `annotate` и других средств ORM.

В модели истории приёмов используются статусы на основе `TextChoices`.

В модели расписания предусмотрены вычисляемые поля:

- `total_minutes` — время приёма, представленное в минутах от начала суток;
- `is_night` — признак ночного времени приёма.

Для лекарств используется уникальный URL-идентификатор `slug`, формируемый на основе названия с транслитерацией.

## База данных и миграции

В проекте используется SQLite. Структура базы данных управляется миграциями Django.

После получения обновлений проекта выполни:

```bash
python manage.py migrate
```

Перед обновлением существующей базы данных рекомендуется создать резервную копию файла `db.sqlite3`.

Не удаляй существующие миграции и не пересоздавай базу без необходимости: они обеспечивают последовательное обновление структуры данных и сохранение существующих записей.
